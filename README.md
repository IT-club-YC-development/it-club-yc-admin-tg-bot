# OptiBot — MVP

Мінімальний каркас OptiBot — Telegram-бота для модерації, який містить робочу команду `/start`, базову структуру застосунку та узгоджені інтерфейси для подальшої реалізації роботи з базою даних.

## Технологічний стек

- **Python 3.11+** — мова програмування.
- **aiogram 3** — асинхронна бібліотека для роботи з Telegram Bot API.
- **SQLAlchemy 2 (async)** — ORM для майбутньої роботи з базою даних. Контрактний шар поки не прив'язаний до конкретної СУБД.
- **`Protocol` та dataclasses** — типізовані контракти між компонентами застосунку.

## Запуск проєкту

### 1. Клонування репозиторію

```bash
git clone <URL_РЕПОЗИТОРІЮ>
cd OptiBot
```

### 2. Створення віртуального середовища

```bash
python -m venv .venv
source .venv/bin/activate
```

### 3. Встановлення залежностей

```bash
pip install -r requirements.txt
```

### 4. Налаштування змінних середовища

```bash
cp .env.example .env
```

Додайте токен Telegram-бота до файлу `.env`:

```env
BOT_TOKEN=ваш_токен_бота
```

**Не публікуйте токен і не додавайте файл `.env` до Git.**

### 5. Запуск

```bash
python bot.py
```

Після запуску надішліть боту команду `/start` у Telegram.

## Архітектура та правила розробки

1. **`handlers/`** — обробка вхідних повідомлень і команд Telegram, перевірка формату вхідних даних. Не містить бізнес-логіки.
2. **`services/`** — бізнес-логіка та правила роботи застосунку. Обробники не звертаються до SQL або репозиторіїв безпосередньо.
3. **`database/repositories/`** — інтерфейси для доступу до даних. Реалізації репозиторіїв поки не створені.
4. **Асинхронність** — усі операції, що потенційно потребують введення-виведення (I/O), мають бути асинхронними.
5. **Час і дати** — використовуються об'єкти дати й часу з часовим поясом; для зберігання та обробки використовується UTC.
6. **Ідентифікатори Telegram** — ID користувачів і чатів зберігаються як `int`. `username` не використовується як унікальний ідентифікатор.
7. **Облік покарань** — запитане покарання, його статус і результат виконання через Telegram API зберігаються окремо. Помилка застосування не повинна позначатися як успішне виконання.
8. **Зміна контрактів** — зміни публічних інтерфейсів необхідно узгоджувати через Pull Request (PR) та одночасно відображати в `docs/CONTRACTS.md`.

## Поточний стан MVP

Реалізовано:
- базову структуру проєкту;
- команду `/start`;
- початкові контракти для майбутньої роботи з даними.

Ще не реалізовано:
- підключення до бази даних і міграції;
- застосування покарань через Telegram API;
- перевірку прав користувачів;
- журналювання модераторських дій;
- інші команди бота;
- автоматичне завершення строку дії покарань;
- повну обробку помилок та інтеграційні тести.

## Принцип розробки

OptiBot розробляється поетапно. Спочатку узгоджуються структура проєкту та інтерфейси компонентів, а потім функціональність реалізується окремими завданнями.

**Поточна версія — це початковий каркас (scaffold), а не готовий до повноцінного використання модераційний бот.**
