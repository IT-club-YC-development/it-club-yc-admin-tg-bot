# Database specification

PostgreSQL, SQLAlchemy 2 async, `asyncpg`, and Alembic. There are four tables.

## `users`

One row per Telegram user per chat. Composite primary key: `(chat_id, user_id)`.
- `chat_id BIGINT NOT NULL`
- `user_id BIGINT NOT NULL`
- `username VARCHAR(32) NULL`
- `first_seen_at TIMESTAMPTZ NOT NULL`
- `joined_at TIMESTAMPTZ NULL`

`first_seen_at` is set on first observation and must not be reset on later updates. `username` can change.

## `actions`

One row per moderation action.
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `chat_id BIGINT NOT NULL`
- `user_id BIGINT NOT NULL`
- `moderator_id BIGINT NOT NULL` (the bot ID may be used for automatic actions)
- `action_type VARCHAR(16) NOT NULL`: `warn`, `mute`, `ban`
- `reason TEXT NULL`
- `created_at TIMESTAMPTZ NOT NULL`
- `expires_at TIMESTAMPTZ NULL`
- `revoked_at TIMESTAMPTZ NULL`

Warnings remain in history. A warning counts only if its `action_type='warn'`, `created_at >= now - interval '30 days'`, and `revoked_at IS NULL`. A temporary mute/ban has an expiry. A permanent ban has no expiry. `revoked_at` records revocation without deleting history.

## `moderators`

One custom role per user per chat. Composite primary key `(chat_id, user_id)`.
- `chat_id BIGINT NOT NULL`
- `user_id BIGINT NOT NULL`
- `role VARCHAR(16) NOT NULL`: `moderator` or `admin`
- `granted_by BIGINT NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL`

Telegram administrator status and OptiBot's custom role are distinct. The command implementation must follow the project's agreed permission policy.

## `action_logs`

One row per attempted or completed operation.
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `chat_id BIGINT NOT NULL`
- `actor_id BIGINT NOT NULL`
- `target_user_id BIGINT NULL`
- `action VARCHAR(32) NOT NULL`
- `result VARCHAR(16) NOT NULL`: `success`, `failure`, `unknown`
- `details TEXT NULL`
- `created_at TIMESTAMPTZ NOT NULL`

Use `unknown` when a network timeout means the Telegram result cannot be confirmed. Never log a failed Telegram API call as a successful punishment.

## Indexes and integrity

Add an index on `actions(chat_id, user_id, action_type, created_at)` for warning counts and history. Consider indexes for `action_logs(chat_id, created_at)` if log browsing is added. Do not cascade-delete moderation history when a user row is removed. Keep timestamps timezone-aware.

## Query contract

See `CONTRACTS.md`. Database query functions accept an `AsyncSession` as their first argument. They `flush()` changes but do not commit; transaction ownership belongs to the caller.
